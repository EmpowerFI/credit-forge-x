# The WhatsApp entry layer — the pieces that can exist before the code

**Written for:** the founder, and whoever submits these to Meta. Companion to [STUDY-WHATSAPP.md](../STUDY-WHATSAPP.md), which carries the reasoning. This directory holds the artefacts: the check-in form, the message templates and the consent wording. None of it is wired to anything, and all of it moves to the private repo when that exists.

## Two findings that change the plan

**A Flow with no endpoint is enough, and that is a week back.** [STUDY-WHATSAPP §4.2](../STUDY-WHATSAPP.md) left this open and budgeted roughly a week for a data endpoint with an encryption key pair. Checked against Meta's own documentation: a Flow without an endpoint generates its routing automatically, ends on a terminal screen whose `Footer` carries a `complete` action, and delivers everything she typed in the webhook as `nfm_reply.response_json`. A check-in needs no live data from the server while she fills it, so none of the endpoint work is needed. Confirm in Flow Builder before relying on it — that is also the authoritative validator for the JSON here.

**Business verification is not required to start, and a test number needs no paperwork at all.** Getting started creates a test WhatsApp Business account and a test phone number with relaxed limits and no payment method, so the whole build can be exercised today. Verification is what the *pilot* waits on, not the build: unverified, a business is capped at about 250 unique customers in a rolling 24 hours for business-initiated conversations, and the display name needs verification to be approved. 250 is far above a first cohort, so even the pilot is not blocked by it — the cap binds on the daily reminder, which is business-initiated, and not on the report link, which [STUDY-ACCESS §3](../STUDY-ACCESS.md) already makes something she asks for.

## What is built, as of 13 October 2026

The receiving half. Nothing sends yet, and nothing needs Meta to be exercised.

| | where | what proves it |
|---|---|---|
| the parser | `platform/supabase/functions/_shared/whatsapp.ts` | 10 Deno tests, in CI |
| the webhook | `platform/supabase/functions/whatsapp-webhook/` | type-checked in CI |
| the tables | `platform/supabase/migrations/` from `20261109000100` on | a run from zero into a scratch database |

**The fortnight check-in is retired.** The first form asked her to remember fifteen days at once and assembled a month from two halves. The daily journal replaced it, and `20261125000000_the_fortnight_is_retired.sql` drops its tables (`whatsapp_checkin_halves`, `whatsapp_flow_tokens`) and the two functions that wrote them, refusing to run if either table holds a row. Its form, `checkin-flow.pt-BR.json`, is gone from this directory; git history keeps it.

**The entry conversation, as a pure state machine.** `platform/supabase/functions/_shared/conversation.ts` decides every reply from the stored row alone -- no clock, no database, no network -- so AC-02, *resumes exactly at the last valid question*, is a property of the data rather than a hope about a session. The rule that produces it: **an answer that is not understood never advances the step**, so a reply three days later lands on the same question by construction. `SAIR` and `AJUDA` work at every point and are never read as answers; a withdrawn consent is not reinstated by saying hello, she starts again from the wording.

She becomes an entrepreneur on the last answer, **in one transaction with her consent record** -- a woman who exists without a consent record is worse than one who does not exist, because the record is what says she was asked. The scopes are **assessment only**: the wording promises a reading of her own month and says nobody sees her figures without her say-so, so partner, investor and impact are false. Widening is a new consent, never a default.

Three things the tests pin that are easy to get wrong: *"não sei"* is an answer and stores null months, while an answer nobody could read is refused and asks again -- merging the two would record "she does not know" for something nobody read; a retried delivery is recognised **before** the machine sees it, because run twice an answer advances two questions and the sector lands under the wrong one; and `+1 415 555 0132` is eleven digits, exactly like a Brazilian mobile written locally.

**The monthly reading.** Built for the fortnight form, which sent it when a month was assembled; nothing sends it since that form was retired, and the weekly reading below runs on the same machinery. The figures come from `packages/checkin-insights` -- pure, versioned, integer-only, computed before any model is involved; a cost she did not know leaves the result *absent*, never zero. The prose is written by Claude Haiku over those figures and accepted only if it passes every check in `_shared/report.ts`: **no number that was not handed over**, in the form it was handed over; never *lucro*, *crédito*, *empréstimo*, *financiamento*, *score* or *inadimplência*; at most two observations, one action. A refused answer is replaced, not repaired, by a reading built from fixed sentences -- and the tests prove that fallback passes the same checks in every kind of month. The model never sees her name, phone or city; her first name is added to the message by code afterwards.

`ai_analyses` holds one reading per month: a retried delivery returns the stored reading without calling the model (AC-03), a model failure becomes the fallback and the month is never sent to the model again (AC-09), and retries stop after three. Prompt version, model, formula version, tokens, cost and -- when the model was refused -- the reasons, which are the sample a human reviews.

Still to build: the baseline and the report link.

**The daily journal replaced the fortnight** (specification: [`diario.pt-BR.md`](diario.pt-BR.md)). Its foundation is in the database: `journal_entries` (one line per sale or expense, with payment method, à vista or a prazo, and a classification that maps to a simple income statement), `journal_days` (a day is kept when it has a line or she said nothing happened), `journal_dre` for any range of days, `journal_month_status` (a month counts when no calendar week in it misses more than one day), and a daily job that assembles each finished, well-kept month into `checkins` for the readiness engine, unchanged. The daily form is built: [`diario-flow.pt-BR.json`](diario-flow.pt-BR.json) is generated from `_shared/journal.ts` (`npx tsx scripts/whatsapp/build-diario-flow.mts`), and a test fails if the two disagree. "Ontem" is the default because the reminder goes out at 9 in the morning about the day before. Sales go in as the day's total per payment method; up to three expenses per form, and another form the same day adds to it. A quiet day is one tap on the reminder's quick reply (`journal_quiet_yesterday`) or the words SEM MOVIMENTO. Every form is answered at once with fixed text from `journal_day_summary`. Streaks and rewards are built: a streak is a run of kept days in which no calendar week misses more than one, its length is the days kept, and each milestone of the latest published programme is earned once, ever (`journal_progress`). The programme is published, frozen and versioned, through `reward_programme_publish` -- callable by the credit platform's admins or an owner of the dashboard's admin layer -- and read with `reward_programme_current`. Version 1 is seeded with the founder's programme (7, 14 and 28 days; the partner's credit card at 60) and placeholder titles. A partner benefit is recorded as `awaiting_consent` until she authorises a share to that partner: she is sent exactly what would go -- recipient, purpose, the indicators of each month, how long -- and answers AUTORIZO or NÃO; AUTORIZAÇÕES lists her shares and ENCERRAR n ends one ([`docs/PASSPORT.md`](../PASSPORT.md), step 3). The rewards screen is in the dashboard (EmpowerFI/empowerfi-dashboard, `/rewards`). The weekly reading is built: `checkin-report` reads a month (`{ checkin_id }`) or a week (`{ entrepreneur_id, week_start }`) with the same figures engine (`insights-v0.2.0`, a week named by its Monday), the same checks and fallback, and `journal_readings` keeps it once per week. It follows the confirmation when she records Sunday -- usually Monday morning -- or, if Sunday never comes, the next day she records; a week is read only if she kept at least three of its days, and compared with the week before only if both were kept on at least six. **Corrections, quiet reasons, coverage.** VER lists today's and yesterday's lines, numbered, and remembers the list (`journal_listings`); APAGAR n voids the line she saw as n -- marked `voided_at` with the message that voided it, never deleted, and left out of every sum. Only today and yesterday, the window she writes in, and never in a month already assembled for credit. A quiet day may say why: `closed` (did not open) or `no_sales` (opened, sold nothing), by the reminder's buttons (`journal_closed_yesterday`, `journal_no_sales_yesterday`) or in words; the DRE counts `days_closed`. The weekly reading ends with a line computed by code: "Você registrou em 24 dos últimos 30 dias". Each closed month is also written down as an immutable, versioned snapshot for the Business Passport ([`docs/PASSPORT.md`](../PASSPORT.md)). **Voice and free text.** A voice note (transcribed by OpenAI) or a plain message is read by Claude into proposed lines, and every amount, date and instalment count must be quoted from her words and is parsed by code (`_shared/spoken.ts`); she confirms the formatted draft with Confirmar or Corrigir before anything is written (`journal_drafts`, `journal_draft_decide`). Audio is never stored; the transcript is cleared on her answer and deleted within 23 hours. Specification: [`diario.pt-BR.md`](diario.pt-BR.md) §1. **The 9 o'clock reminder** is built: `journal-reminder`, called by pg_cron at 12:00 UTC, sends the `lembrete_diario` template to everyone active, enrolled before today, with nothing for yesterday and not reminded about it yet -- once per woman per day, a failed send recorded and not retried (`journal_reminders`). Its quick replies open the form or record a quiet day. **To switch WhatsApp on, follow [`META-SETUP.pt-BR.md`](META-SETUP.pt-BR.md).** The fortnight form and its tables are retired.

## Message templates

Three, and their category is a cost decision rather than a label. A reply inside the open 24-hour service window is free; a template that opens a conversation is billed, and `marketing` is billed at the highest rate and needs opt-in it is easy to lose.

| what | category | when |
|---|---|---|
| `lembrete_diario`, the 9 o'clock journal reminder: Registrar ontem / Não abri ontem / Abri e não vendi | `utility` | business-initiated, once a day, the only recurring cost |
| the consent and welcome message, after she signs up on the web page | `utility` | once per entrepreneur |
| the report link | **none — never a template** | she asks, the window is already open, and it is free. [STUDY-ACCESS §3](../STUDY-ACCESS.md) is why |

**Nothing about credit is ever a template.** Not an offer, not a reminder that she became eligible, not a nudge. That is `marketing` by Meta's classification and it is also the thing the product refuses to do: *being ready and not asking is a complete outcome.* The ethics and the billing agree for once.

## Consent

A new `consent_channel` value — the enum is `('app', 'community')` today — and a new `text_version`, because WhatsApp is not a channel anyone already agreed to. Two things it has to say that the app's wording never had to:

- **Meta sees the conversation.** Meta's Cloud API carries every message, so at the least it knows she is in this programme and when she replies. [STUDY-WHATSAPP §4.4](../STUDY-WHATSAPP.md).
- **Voice and free text go to AI services.** OpenAI transcribes and Anthropic reads them, in the United States, only to propose a record she confirms; the audio is not kept and the text is deleted within 24 hours. Version `whatsapp-2026-11` says so.
- **What arrives, and how often.** One reminder a day, and she can stop them without leaving the programme.

The eighteen already registered in the app re-consent once rather than carrying the old record forward: a migrated consent is the kind of thing that reads fine until someone asks to see what she actually agreed to. [STUDY-ACCESS §7](../STUDY-ACCESS.md).

## What has to exist before any of this collects a single real figure

> **A place for the data has to exist before the data does.**

The production database is [PLAN.md](../PLAN.md) item 1.5 and it is not optional ceremony. Real revenue and household figures cannot land in the hackathon project: its password is published on purpose, one click switches a visitor to any persona, and `seed-demo.mts` opens with `reset_demo_data()`. That is correct for a showroom and disqualifying for a woman's figures.

So the order is: production project → the migrations run from zero into it → then collection. Everything in this directory, and all of the Meta onboarding, runs in parallel with that and none of it touches a real figure.
